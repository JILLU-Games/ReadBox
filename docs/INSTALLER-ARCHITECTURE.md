# ReadBox Installer Architecture

**Status:** Design proposal; no setup web/API runner is implemented
**Version:** 1.0
**Date:** 2026-10-18

This design follows the frozen PostgreSQL-only policy and [Architecture Decisions](ARCHITECTURE-DECISIONS.md). Product requirements live in [Product Plan](PRODUCT-PLAN.md); phase gates are in [Implementation Roadmap](IMPLEMENTATION-ROADMAP.md).

## Existing Foundation and Boundary

The current environment parser accepts PostgreSQL URLs and `AUTH_ENABLED` defaults false. Protected user/admin routes redirect to sign-in when auth is disabled. `src/auth.ts` restricts enabled authentication to development/test. `bootstrapInitialAccount()` is a locked, reset-required initial user creation helper; `scripts/auth/operator.ts` requires local development, a loopback PostgreSQL URL, and an interactive terminal. This existing CLI is not a privileged service installer or a browser setup flow.

The setup surface must not weaken the normal route guards. Before authentication exists, expose only an explicitly designed, local setup boundary with strong one-time authorization and CSRF/origin protections. Do not make admin-only operations publicly callable merely because no admin exists. Design and test this boundary before creating setup routes.

## Administrator Identity and Bootstrap

Use the existing Auth.js `User` identity with a one-to-one `AdministratorProfile`, rather than a separate administrator login. `User` owns login identifiers, password hash, active/reset state, and `AppSession`; `AdministratorProfile` owns application-admin membership, a separate app-level superuser tier, its stable ID, and management timestamps. Credentials are not copied. `getCurrentUser()` and `getActiveAppSession()` resolve the profile from PostgreSQL on the server; route guards use that resolved profile, not client flags. Legacy `User.isStaff`/`isSuperuser` columns are not authoritative and the additive migration does not backfill existing accounts. Existing legacy admins consequently remain non-admin until a separately approved, explicit profile assignment; there is no automatic promotion.

`bootstrapInitialAccount()` validates its input and creates a reset-required `User`, its `AdministratorProfile`, and one-time password-reset token within the existing advisory-locked transaction. The interactive CLI requires development mode, loopback PostgreSQL, an interactive terminal, and rejects `mailstack_dev`. TTY presence does not verify OS identity, so this path grants only an application account in the local operator boundary and must never mint host/installer authority. No web endpoint is added. The profile migration is an additive artifact; it was not executed during the Phase 6.1 verification, and actual applied state is unknown because no database was queried. Synthetic model tests cover mapping; actual referential/concurrency behavior requires an explicitly verified disposable PostgreSQL database.

## Authorization Policy and Operation Boundary

`src/core/setup/authorization.ts` defines anonymous, authenticated application-user, application-admin, and trusted-installer principal categories. `resolveSetupPrincipal()` calls the existing server-side `getCurrentUser()` helper and creates opaque principal objects registered in a module-private `WeakMap`; caller-supplied objects, role strings, headers, cookies, and booleans are not treated as verified. Staff/superuser status produces only an application-admin principal, never installer authority. The trusted-installer category has no issuer, so no such principal can currently be created.

Authorization decisions distinguish allow, deny, unsupported, invalid request, and delegation to existing application route guards. Anonymous inspection permits only the `status-summary` scope; `toPublicSetupStatus()` projects only a validated lifecycle value. Transition validation remains unsupported as an HTTP action. Lifecycle-bound scopes are: `setup:initialize` for `not-started` or `in-progress`, `setup:record-failure` for `in-progress`, `setup:recover` for `failed` or `interrupted`, and `installer:manage` for `completed`. These lifecycle values are policy types only; the current in-memory progress model cannot represent failure/interruption or survive process restart.

`src/core/setup/trusted-operations.ts` is server-only and dependency-injected; absent authorization denies. Code-defined operation entries specify a required scope and supported lifecycle. The runner snapshots and validates input, asks the server authorizer for the exact operation and scope, and requires the returned grant to match operation ID, required scope, trusted-installer category, and allowed lifecycle before execution. Unknown, invalid, denied, or mismatched requests never invoke an executor. Definitions without executors remain unsupported; exceptions return fixed safe codes. There are no production operation definitions, issuer, or concrete authorizer, so the interface performs no host work.

The runner's injected callback is itself a trusted server-code boundary, not proof of authority: `SetupAuthorizationDecision` is a structural object. It has no issuer identity, expiry, nonce, use counter, or revocation state. A server caller that fabricates or reuses a matching `allow` result can pass the runner's shape checks. This callback is not reachable from request data in the current project because no route or production call site exists; default construction without an authorizer denies. Never wire a client-controlled decision or an unverified provider. Expiry, revocation, and single-use enforcement require a future verified issuer and durable transactional grant state; they are not implemented by the current runner.

Before any setup HTTP endpoint, approve the one-time bootstrap proof/issuer and post-setup administrator or step-up verification; define durable lifecycle state, concurrent setup claims, replay/idempotency, and failed/interrupted recovery; and implement route-level server identity checks, CSRF/origin protection, input validation, rate limits, and a safe status/progress projection. Routes must resolve principal and lifecycle on the server, never from request data. The existing progress model is in-memory only. No persistent setup state is implemented.

**Recommendation — DESIGNED, NOT IMPLEMENTED:** use a dedicated local installer agent whose caller identity is verified by an OS-protected channel (for example, platform ACLs on a local IPC endpoint), not by TTY presence, loopback HTTP, a client-supplied role, or an application-admin profile. Run it as a dedicated OS identity with only the allowlisted privileges required for supported operations. The agent is the trusted-installer principal; the web application and application administrators are not.

For each request, the agent obtains the peer identity from the OS-authenticated IPC mechanism and checks it against an explicitly configured local-operator allowlist; it creates an immutable server-side principal record itself, never from caller-supplied role data. If the platform cannot authenticate the peer or the identity is not enrolled, deny. The exact enrollment proof and group/identity policy are platform decisions that require approval.

For each admitted operation, the agent should issue an unpredictable, short-lived capability bound to the verified local identity, setup instance, one operation ID, one exact operation/scope, the expected setup revision, and the intended worker. Keep the capability verifier and consumed/revoked state in the single active agent process; serialize consumption, mark it consumed before dispatch, reject expired/revoked/replayed or mismatched grants, and invalidate every outstanding grant on agent restart. Grants are not bearer tokens for browser storage or logs. A browser-driven operation requires a separately reviewed local pairing mechanism that binds the browser session to the agent; until approved, no browser route may mint or broaden a grant. If a design requires grants to survive agent restart or multiple active agents, it must first define durable atomic consumption using the existing PostgreSQL database and cannot proceed before that database is available.

The agent must independently validate the operation registry and inputs; authority is limited to a single approved operation, not a wildcard scope. `isStaff`, `isSuperuser`, `AdministratorProfile`, session presence, loopback origin, and the existing operator CLI's TTY check grant no host authority. Application administrators may receive application-level access only. Grant failure, issuer unavailability, invalid OS identity, state mismatch, expiry, or uncertainty denies the request and causes no operation; no fallback token or direct shell path is allowed. Explicit local revocation and agent shutdown/restart invalidate unused grants. Operation results still require durable ledger reconciliation and independent postcondition verification.

**Approval gate:** this recommendation is not authorization to build an agent or expose a route. Product approval is required for supported OSes, the OS identity/enrollment mechanism, process account and privilege set, local pairing/handoff, agent update/revocation policy, and the trust boundary between the web process and worker. Until those are verified, keep the issuer absent and all host operations default-deny. Do not use a permanent environment token, universal bootstrap token, browser-visible privileged secret, or unauthenticated privileged endpoint.

## Initial Administrator Bootstrap Contract

**Existing behavior: IMPLEMENTED.** `AdministratorProfile` is the authoritative application-admin membership linked to canonical `User`; it does not duplicate credentials. `bootstrapInitialAccount()` validates details and, under a PostgreSQL advisory transaction lock, creates a reset-required user, profile, and hashed one-time password-reset token atomically. It first checks for an empty user table. Concurrent attempts serialize; one can create the first account and later attempts return no account-created result. A transaction failure rolls back the user, profile, and token together. The interactive operator CLI is currently development-only, loopback-PostgreSQL-only, TTY-gated, and rejects `mailstack_dev`; it is not production bootstrap or installer authority. A TTY is not proof of OS identity.

**Recommended first-run flow: DESIGNED — NOT IMPLEMENTED as Guided Setup.** First establish a trusted local operator/agent boundary and a reachable, operator-provisioned PostgreSQL database. Then use an operator-authorized bootstrap action to create exactly one application administrator through the existing locked helper, show the reset token once through an approved local protected channel, require password reset, and verify sign-in before granting application-admin access. The application-admin profile never grants host-operation authority. No public registration, anonymous privilege-grant route, automatic legacy-role promotion, or host capability is part of this flow.

Duplicate/concurrent bootstrap must return a generic already-initialized result without identifying the existing account. If interrupted before transaction commit, retry may safely attempt bootstrap; if interrupted after commit but before the reset token is received, do not rerun or delete the account. Recover by issuing a new reset token through a separately trusted operator recovery path, then verify reset and sign-in. The current CLI has a local reset action but shares its development-only restrictions; production recovery is **BLOCKED — APPROVAL REQUIRED**. A browser endpoint may replace neither this boundary nor the existing helper's reset-required semantics until production authentication, local operator proof, CSRF, replay protection, and token delivery are reviewed.

Future acceptance: exactly one profile-backed admin under concurrent requests; atomic rollback on any partial failure; no public account creation; reset-token hash only at rest and one-time local delivery; safe recovery after lost output; no elevation from legacy flags or app-admin membership; and no host authority from bootstrap.

## Lifecycle and Persistence Contract

The pure planner in `src/core/setup/lifecycle.ts` defines `not-started`, `in-progress`, `completed`, `failed`, and `interrupted`. It produces a transition **plan**, not a persisted update, authorization grant, or proof that an operation succeeded.

### Proposed PostgreSQL Lifecycle Shape (Design Only)

Use only the existing PostgreSQL database. The minimum proposed schema is three related tables; exact Prisma names, column types, checks, schema placement, and migration order remain subject to review before implementation.

| Proposed table     | Minimum data and constraints                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setup_instances`  | A singleton key with a uniqueness/check constraint; stable setup-instance UUID; lifecycle; nonnegative monotonic revision; active and failed operation IDs; current lease generation/expiry and heartbeat; last transition ID; created/updated timestamps. State checks keep active/failed operation references consistent with lifecycle.                                                                                                                                                        |
| `setup_operations` | Operation UUID; setup-instance FK; operation kind and required scope; expected and resulting revisions; status (`pending`, `running`, `succeeded`, `failed`, `recovery_required`); unique hash of a server-generated high-entropy idempotency key; canonical fingerprint of non-secret request metadata; allowlisted safe result/error code; lease generation, expiry, heartbeat, started/finished/created/updated timestamps. Keep only the bounded data needed to resolve retries and recovery. |
| `setup_milestones` | Setup-instance FK; finite milestone key; verified-by operation FK; verification time; allowlisted verification result code; unique `(setup_instance_id, milestone_key)`. Rows mean server-side postconditions were checked, not merely that a caller requested a step.                                                                                                                                                                                                                            |

Do not store passwords, credentials, bootstrap/reset tokens, raw command output, arbitrary request bodies, message/customer content, or raw errors. Never persist secret values or low-entropy hashes for request comparison. Idempotency keys must be random and generated/issued by trusted server code. Fingerprints may cover only a versioned canonical allowlist of non-secret request fields and operation/scope/revision; secret-bearing inputs are excluded and must be supplied through a separately approved ephemeral execution channel. If a secret-bearing attempt has an uncertain outcome, mark it `recovery_required`; do not retry it blindly.

The three-table shape is a proposal, not an authorization to add models or migrations. Exact singleton initialization, existing Prisma schema ownership, database grants, retention, and how safe audit events align with the current `AuditLog` still require review. Any future schema/migration must use the same PostgreSQL database and pass separate approval and synthetic migration tests before it is implemented.

### Transaction, Replay, and Recovery Protocol

For each state-changing request, a future service must run a short PostgreSQL transaction that (1) resolves the idempotency-key hash and compares operation, scope, expected revision, and non-secret request fingerprint; (2) locks the single setup row or performs an equivalent conditional revision/state update; (3) claims the operation row under unique constraints; (4) changes the lifecycle snapshot, operation ledger, and verified milestone rows together; and (5) commits. Exactly one CAS may advance a given revision. A stale revision returns conflict. Same key plus same metadata returns the previously stored operation status/result; same key with different metadata is rejected. A unique-key race rolls back, then reloads the winning row in a new transaction. Never report a duplicate request as a new independent success.

Do not hold a database transaction open while performing Docker/OS work. Commit an operation reservation and lease first; execute outside the transaction using a stable operation ID and an idempotent executor; independently verify postconditions; then use a second transaction to commit result, milestones, and lifecycle only if the operation ID, lease generation/fencing token, and expected revision still match. The external executor must detect/reconcile an already-applied effect by operation ID and postcondition rather than repeat a non-idempotent effect.

After a crash, an expired lease/heartbeat permits marking the operation `recovery_required`, not automatic re-execution. Read-only postcondition checks may classify it as completed, failed, or unknown. Unknown/partial outcomes require a scoped operator recovery decision; no implicit resource deletion. Completion requires all required verified milestones and the active operation to match, and becomes terminal for ordinary transitions. Any exceptional completed-state repair would need a separately approved recovery authority and audited policy, not a normal setup retry.

The transaction, constraints, leases, idempotency ledger, fencing, recovery, and crash behavior above are **specified only**. The current planner now fingerprints the last non-secret transition payload, distinguishing an identical immediate retry from reuse of that last key with changed input. This is in-memory and covers only the latest transition; it does not provide durable replay protection or concurrency safety. Its competing-plan test intentionally demonstrates that two processes can both produce a plan from one snapshot. PostgreSQL CAS and the durable operation ledger are required before claiming persistence guarantees.

| Transition                               | Required conditions                                                                            | Required scope                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `not-started -> in-progress`             | New operation ID; expected current revision; atomic setup claim.                               | Trusted installer with `setup:initialize`                |
| `in-progress -> completed`               | Same active operation; all `SETUP_STEPS` independently verified by trusted server-side work.   | Trusted installer with `setup:initialize`                |
| `in-progress -> failed` or `interrupted` | Same active operation; trusted worker observed a sanitized failure or expired operation lease. | Trusted worker with `setup:record-failure`               |
| `failed` or `interrupted -> in-progress` | Failed operation ID matches durable state; recovery postconditions verified; new operation ID. | Operator-verified trusted installer with `setup:recover` |
| `completed -> any other state`           | Not allowed through ordinary setup transitions.                                                | None                                                     |

The planner emits the required scope but does not authorize the caller. Every transition above requires a separately verified trusted principal; app users/admins, request fields, and status-summary grants cannot satisfy it. The planner does not itself verify operation evidence.

Before persistence exists, `revision` and `lastTransitionId` let the pure policy report stale revisions and immediate duplicate transition IDs. They do not serialize processes, survive restarts, or deduplicate all historical requests. Persistent implementation must use the single PostgreSQL database and atomically compare-and-swap the expected revision while recording the transition/idempotency key and resulting state in the same transaction. It must durably record active operation identity/lease, lifecycle, revisions, and sanitized outcome; no credentials or secret values belong in lifecycle records or logs. A uniqueness constraint or equivalent transactional ledger must make one idempotency key map to one operation and result.

Concurrent setup claims must have one winner. A stale revision or duplicate request must return conflict/replay and reload durable state; it must not be treated as an independent successful operation. On restart, an `in-progress` operation is not automatically retried: first determine from durable lease/heartbeat and verified external postconditions whether it completed, failed, or needs operator recovery. Mark interruption only after an owner lease is proven expired under transaction/lock. Recovery requires an operator-verified trusted principal, is scoped to the recorded failed operation, idempotent, audited with redacted metadata, and must never delete/drop resources as an implicit repair. Completion is irreversible through ordinary requests.

These transaction, lease, replay-ledger, audit, and restart guarantees are **specified only**. No setup model, migration, database access, or persistence adapter is implemented. The planner trusts that its server-only caller supplies truthful operation verification; it must never be exposed directly to browser-controlled evidence.

## State Machine Proposal

Persisted state must not be added until its threat model and storage location are approved. The current code contains two related but distinct concepts: the aggregate lifecycle (`not-started`, `in-progress`, `completed`, `failed`, `interrupted`) in `lifecycle.ts`, and the ordered fine-grained milestones in `progress.ts`. They are not competing state machines: the aggregate lifecycle owns operation/revision/recovery state, while milestone rows record independently verified postconditions. The canonical milestone order already present in code is:

`environment-validated -> database-requested -> database-created -> database-verified -> schema-verified -> administrator-created -> completion-verified`

Every persisted milestone must map to exactly one versioned key from this list (or an explicitly approved future version); callers cannot skip or reorder it. `completed` is permitted only after fresh verification of all required milestones. The proposed table shape and transaction contract above remain **DESIGNED — NOT IMPLEMENTED**.

A failure records a bounded, sanitized failure state and a resumable step, never raw credentials, command output, SQL, password hashes, or connection strings. Retries are idempotent and re-check actual state. Terminal completion is set only after a fresh verification of database connectivity, schema readiness, least-privilege app access, and an active initial administrator. Recovery is an explicit operator action; it does not silently drop databases or accounts.

The current Phase 5 foundation is only a pure in-memory ordered milestone policy in `src/core/setup/progress.ts`. It rejects skipped/malformed milestones, treats completed-milestone replay as idempotent, and requires a final verification milestone. It does not establish that an operation actually succeeded; callers must verify postconditions before advancing it. No persistence, route, setup worker, or database operation is implemented.

The proposed four UI steps group those milestones; they do not change milestone order or authorize side effects. Step 1 is read-only and assumes PostgreSQL has been provisioned and can be checked. Database creation is out of scope until the PostgreSQL-ledger bootstrap dependency is resolved. Step 2 follows the initial-admin contract above. Any future credential input must be server-validated and delivered only through an approved protected channel; it must not be stored in lifecycle records or logs. Preserve the operator CLI until an approved and tested replacement exists.

## Mail Configuration and Readiness Contract

**Status: DESIGNED — NOT IMPLEMENTED; provider and operational contract require approval.** Keep setup configuration provider-neutral. A future adapter accepts validated domain/mailbox intent and opaque references to secrets, returns normalized non-secret configuration metadata, performs bounded connection/service checks, and verifies readiness through separately defined postconditions. Domain and mailbox values must be normalized and validated server-side; mailbox credentials remain distinct from application login credentials. Do not persist secret values, password-reset tokens, raw provider responses, or low-entropy secret hashes in Prisma, progress records, errors, or logs. Secret storage, retrieval, rotation, and delivery to an approved worker require an explicit product decision.

Expose distinct states rather than one ambiguous “valid” flag: `configuration-invalid`, `configuration-valid`, `service-unreachable`, `service-reachable`, `delivery-unverified`, `delivery-verified`, and `blocked` (or a reviewed equivalent). Syntactic/configuration validity proves only that accepted fields satisfy the contract; connectivity proves only that a bounded service check succeeded; delivery readiness requires an approved end-to-end test and independent verification. A running process or successful configuration render is not proof of delivery. Return stable field/error codes and sanitized guidance, never secrets, raw command output, credentials, or host paths.

The adapter contract should separate `validateConfiguration`, `checkService`, and `verifyReadiness`; each has bounded typed inputs/outputs, deadlines, and safe error categories. No provider, Postfix/Dovecot version, DNS/TLS policy, routing/authentication model, credential store, or delivery probe is selected here. **BLOCKED — APPROVAL REQUIRED:** approve supported provider/services and versions, DNS/TLS/port expectations, delivery-test method and recipient, secret storage/rotation, and the meaning/retention of readiness evidence before implementation.

## Setup API and CSRF Boundary

**Status: DESIGNED — NOT IMPLEMENTED.** The only current API file is the Auth.js route; no setup route exists. Proposed boundaries are: (1) a read-only public status projection limited to a generic setup-required/completed indicator, with no host inventory, account existence, error detail, configuration, or operation history; (2) authenticated administrator reads for application configuration/status; (3) state-changing configuration/bootstrap requests only through the separately approved bootstrap or authenticated application-admin boundary; and (4) host-operation, retry/recovery, and completion requests only through a server-verified operation-scoped installer capability. Detailed progress is private. Do not create public registration or an unauthenticated privilege-grant endpoint.

Cookie-authenticated mutations require a session-bound CSRF token, exact same-origin `Origin`/`Host` validation, Fetch Metadata checks, `SameSite` cookies as defense in depth, JSON content-type enforcement, and no permissive cross-origin policy. CSRF controls do not replace authentication or installer authorization. Validate strict schemas, bounds, enums, operation IDs, expected revisions, and idempotency keys on the server; derive principal and lifecycle from trusted server state, never request fields. Apply rate limits to bootstrap attempts, failed authentication, token/grant consumption, status abuse, and retries, with bounded counters and sanitized responses. Return stable safe errors and correlation IDs only; never expose stack traces, SQL, secrets, host paths, arbitrary process output, or sensitive setup details.

All mutations require replay/idempotency protection and the corresponding operation scope. Read-only public status may omit CSRF only if it remains genuinely read-only and its projection stays non-sensitive; private status/progress requires authentication. Retry/recovery must use the original operation identity and expected revision, verify postconditions, and refuse uncertain side effects rather than blindly re-execute. Completion is a state-changing action allowed only after durable milestone verification. Unknown routes/actions fail closed. Anonymous requests cannot bootstrap an account, configure mail, invoke a host operation, retry/recover work, or complete setup.

## Host Operation Registry and Verification

**Status: DESIGNED — NOT IMPLEMENTED; no production registry or executor exists.** Define each operation in code with a unique fixed ID, exact required scope, lifecycle preconditions, typed input validator, bounded typed output schema, timeout, resource-ownership predicates, and independent postcondition verifier. Separate four stages: create a side-effect-free plan; authorize the exact operation and revision; execute through the isolated least-privilege worker; and verify resulting state through an independent check before recording success. The browser supplies typed intent only, never command strings, SQL, paths, arbitrary flags, service names, or executable names.

Unknown or unregistered operations, missing executors, unsupported platforms, invalid inputs, unverified ownership, unavailable authorization, timeouts, and ambiguous outcomes must fail closed without fallback behavior. Do not give the Next.js process a root identity or Docker socket by default. Worker IPC authenticates the caller and validates operation ID, schema version, grant, deadlines, cancellation, and bounded output. Logs and audit events include only correlation/operation IDs, actor class, safe outcome code, timestamps, and allowlisted non-secret metadata; redact credentials, tokens, request bodies, process output, connection strings, and customer data. A successful process exit is not a successful operation until its postcondition is verified.

Acceptance for the future implementation: tests prove app roles cannot acquire host authority; forged, expired, revoked, replayed, wrong-scope, wrong-operation, stale-revision, and wrong-platform requests never execute; same-key exact retries return the existing operation; changed-input reuse conflicts; competing claims have one winner; worker crashes require reconciliation; unsupported operations fail closed; and logs/errors contain no secret material. No host mutation, Docker/OS/network/DNS/mail action, or actual setup route is authorized by this design phase.

## Compact Guided Setup Flow

**Proposed UX: four steps; DESIGNED — NOT IMPLEMENTED.** (1) System readiness: read-only prerequisite scan and PostgreSQL connectivity/schema/least-privilege checks. (2) Initial administrator: operator-controlled bootstrap and verified first sign-in; do not expose public registration. (3) Domain and mail configuration: validate provider-neutral settings and store only approved secret references. (4) Verification and completion: independently verify database/schema, active administrator, service checks, and approved delivery evidence. Keep host provisioning behind the separately approved installer-agent boundary; do not make step 1 mutate the host.

The preliminary preference is out-of-band PostgreSQL provisioning (**PROPOSED — NOT APPROVED**). This avoids asking a not-yet-durable PostgreSQL lifecycle ledger to record creation of its own database, but the lifecycle contract still lists `database-requested` and `database-created`. Those milestones remain unresolved until their semantics are formally reconciled with operator provisioning; do not mark them complete by assumption or authorize wizard database creation. Any alternative requires explicit product/security review and must preserve the single-PostgreSQL policy. No second database or in-memory success claim is allowed.

The four-step sequence is viable if step 1 establishes prerequisites without mutation and the local installer identity is available before any host action. Initial application-admin creation remains a separate trust domain from host authority. If no approved local pairing exists, host operations stay unavailable from the UI and the user flow must stop with a safe blocked state rather than claim completion.

## Trusted Operation Runner

The browser submits typed intent, never shell text, SQL, paths, service names, or arbitrary flags. A server-side coordinator validates the current setup state and maps intent to a finite allowlist of operations. Prefer a dedicated, narrowly privileged setup worker for long-running or privileged work; do not give the Next.js process root or Docker socket access by default. Worker IPC must authenticate the caller, validate an operation ID and schema, enforce timeouts, and return only bounded structured progress/results.

Each operation has an idempotency key, explicit ReadBox resource ownership, preconditions, postcondition checks, timeout, cancellation policy, bounded output, and recovery instructions. Unknown state fails closed. Never interpolate user input into a command. If a required operation cannot be represented safely by a fixed typed API, it is not available through the UI.

## PostgreSQL Bootstrap and Least Privilege

PostgreSQL is the sole database system. Use the existing Prisma/PostgreSQL foundation where compatible. Separate bootstrap authority from application runtime authority: the bootstrap credential is server-side and short-lived or otherwise strongly protected; the application role receives only required schema/table privileges and does not own schemas or perform routine DDL. Migrations run through a separately controlled owner role. Avoid logging URLs or credentials.

Before any database integration test, configure and verify a newly created, dedicated synthetic loopback database. Explicitly reject `mailstack_dev`, non-loopback endpoints, production endpoints, and unknown database names. Never infer test-database safety from environment defaults. This document does not authorize creating or connecting to any database.

## Resource Ownership and Discovery

The default deployment uses a dedicated Compose project, ReadBox-specific labels/names, dedicated persistent volumes, and dedicated networks for supported pinned services. Names and labels must be checked for collision before creation. Teardown only removes resources positively verified as created and owned by ReadBox; no wildcard pruning or shared-volume/network cleanup.

Host scanning is read-only. It distinguishes detected, compatible, reusable, missing, unsupported, and unverified. Reuse requires evidence for version, ownership, configuration compatibility, access boundaries, ports, storage, and impact. Secret-bearing configuration is never displayed or copied into logs. Detection alone never authorizes change.

## Progress, Errors, and Recovery

Progress uses an operation identifier and finite stages, not arbitrary process output. Error responses contain stable safe codes and actionable guidance without stack traces, SQL, credentials, paths that reveal host layout, or customer data. Logs include correlation IDs, operation state, safe result codes, and timestamps only. Retention and access are restricted.

On restart, recover operation state and re-check its postcondition before retry. A partially created resource is adopted only if ownership and expected configuration are verified; otherwise stop for operator review. Never report success until verification passes. Recovery must be documented and must not destroy existing mail or unrelated resources.

## Threat Model and Acceptance

Threats include unauthenticated setup abuse, CSRF, replay, race conditions, command injection, path traversal, privilege escalation, Docker socket compromise, secret leakage, confused-deputy resource cleanup, partial failure, and unsafe restore. Controls include one-time authorization, server-side validation, CSRF/origin protections, typed allowlists, least privilege, explicit ownership, idempotency, output redaction, bounded operations, and verified postconditions.

Acceptance requires tests for unauthorized/replayed requests, concurrent setup, state transition rejection, partial failure and retry, sanitized errors, resource-name collisions, read-only discovery, and worker authorization. Database integration tests require an explicitly verified disposable synthetic loopback database. No host mutation or deployment is part of Phase 5.
