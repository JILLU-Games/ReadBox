# Data Migration Risk Assessment and Rehearsal Plan

> **Current-documentation reconciliation — 2026-11-20:** This page preserves a **historical design, migration, or phase snapshot**. Its dated status, legacy Django/MariaDB references, proposed tasks, and older runtime descriptions are **not current ReadBox implementation claims**. The active product is Next.js 16 / React 19 with one PostgreSQL database, inbound-only Postfix/Dovecot, the implemented browser first-admin flow, and optional Manual Mode DNS onboarding. Consult the [current architecture](dev/architecture.md), [current feature guides](users/features/index.md), and [verification report](reference/coverage-and-verification.md) for code-backed behavior. The 17-gate stable production-release decision remains **NO-GO**.

> **Authoritative database policy:** ReadBox uses exactly one PostgreSQL database for all application and database-backed mail-server management data. Prisma remains the application ORM. Any future Postfix/Dovecot database integration must use this same PostgreSQL database, with separate schemas and least-privilege roles where supported, after installed versions, configuration, schema, and lookup contract are verified. Do not add or connect MariaDB, MySQL, SQLite, or a second database. Maildir and message/attachment files remain on the filesystem. Any legacy multi-database descriptions below are historical/source context only and are superseded as target architecture.

## Status and Scope

Phase 4 Prisma schema and initial SQL are complete. The isolated PostgreSQL 16.14 Phase 4.1 schema-only rehearsal passed. Phase 4.2 risk assessment and this data-rehearsal plan are complete. No source-data migration or source-data rehearsal has been performed, and no importer implementation or data-import command has been established. Production access, production migration, cutover, and Phase 5 remain unapproved.

The Phase 4.1 rehearsal proved only that the SQL migration executes on isolated test PostgreSQL 16.14 and creates the expected schema. It did not test source-data conversion, row counts, ID preservation, password verification, production collation, file references, backup restore, or rollback. PostgreSQL `lower()` is not full Unicode casefold: `Straße` and `STRASSE` remain distinct under the tested behavior. Production collation, ID ranges, password compatibility, sessions, backup/restore, and rollback remain untested.

## Safe Defaults and Mandatory Approval Gates

The following are proposed safe defaults and do not authorize source access, fixture creation, importer implementation, or a rehearsal. This scope rule takes precedence over any broader wording in the mapping, risk table, validation classes, or sequence below: do not inspect, count, copy, or import source sessions; do not access or inspect source password hashes; and do not execute sequence resets or next-generated-ID tests against a sanitized-source fixture. Production access, production migration, cutover, and Phase 5 remain unapproved.

- Keep Django sessions empty. Source sessions are out of scope; any later cutover invalidation and re-login policy requires separate approval.
- Exclude Postfix/Dovecot MariaDB, contact SQLite, Maildir, attachment/media bytes, and other unmapped stores from this PostgreSQL rehearsal.
- Do not dual-write, silently coerce values, merge collisions, or discard rejected records. Preserve mapped IDs and UUIDs where values pass preflight.
- Use only synthetic credentials and password hashes in synthetic tests. No source password hash is permitted in a rehearsal fixture.

Before any fixture is created or rehearsal begins, require recorded approval from named data-owner and security approvers. Approval must cover fixture provenance and scope, sanitization owner and validation evidence, enforced production disconnection and outbound network denial, artifact access/retention/deletion, and the rehearsal authorization. Until each approver, decision, and evidence is recorded, mark it `UNKNOWN / REQUIRES HUMAN APPROVAL` and do not proceed.

Fixture validation must reject the entire fixture and stop immediately if any prohibited secret, credential, password hash, session data, or identifying content is found. Do not remove the offending value in place and continue. A newly prepared fixture requires renewed named, recorded approval and complete revalidation.

Isolation must have no production connectivity or production credentials and must enforce outbound network denial. Verify the denial before fixture handling and before rehearsal execution; prohibit external data egress, including transmission to AI systems or third parties.

Before fixture creation, name an artifact owner and approver and record the approved retention period, protected storage/access controls, and deletion evidence procedure. The artifact inventory must include fixtures, logs, checkpoints/manifests, temporary files, reports, backups, and isolated test target data. At the retention deadline, delete all in-scope artifacts and require verified deletion evidence; retain only evidence explicitly permitted by the approved policy. No fixture creation or rehearsal is authorized until every gate is evidenced.

## Proposed Importer Contract (Not Implemented)

The importer must operate only on one immutable, approved fixture and a reviewed mapping. Before writes, preflight source schema/migration identity, ID and signed `BIGINT` bounds, foreign keys, uniqueness/collation collisions, nullability, lengths, statuses, JSON/IP values, and timestamp semantics. Unsupported values and conflicts are rejects, not candidates for silent transformation.

Use deterministic table and row ordering, bounded batches, and one database transaction per batch. A batch either commits completely or rolls back completely. Import in dependency order: users and domains; mailboxes; policies, memberships, and login attempts; messages; attachment metadata; audit logs, heartbeats, and site settings. Keep sessions empty and require an approved disposition for each included framework table. Use inserts with explicit mapped IDs/UUIDs; do not overwrite differing target rows with upserts.

Persist a batch-completion marker only after its transaction commits. On restart, require identical fixture and mapping fingerprints and inspect target state inside the isolated environment: no rows for the batch means it may be retried; all expected rows present and matching means it is already committed; partial presence or any mismatch means stop and discard the entire scratch target before a fresh run. A changed fingerprint, unexpected uniqueness conflict, or failed transaction also stops the run. Do not repair partial batches in place or continue past conflicts. This rule handles a crash between commit and checkpoint without creating silent duplicates or inconsistent rows.

Future importer specification must define sequence handling after explicit-ID inserts, including empty-table behavior. This is a specification requirement only: do not execute sequence resets or next-generated-ID tests against a sanitized-source fixture or production database. Test sequence reset and next-generated-ID behavior only in a newly created isolated synthetic database with synthetic records. This does not authorize importer implementation or execution.

Perform detailed reconciliation only inside the isolated environment. Compare counts, primary-key/UUID sets, foreign keys, distributions, timestamps, JSON, counters, and any approved file metadata there. Do not export row-level digests, identifiers, or sensitive comparison results. Export only aggregate results explicitly approved by security. Apply the same redaction rules to logs, errors, checkpoints, and reports. Report rejected-record counts only as security-approved aggregates; any unapproved rejection fails the rehearsal.

## Synthetic-Only Test Requirements

Before a sanitized-source rehearsal can be considered, synthetic tests must cover batch atomicity; failures before, during, and after commit; restart with identical and changed fingerprints; absent, fully present, partial, and mismatching batches; duplicate/unique conflicts; FK ordering and orphan rejection; empty and populated sequence behavior; signed `BIGINT` boundaries; null versus blank, length/status/JSON/IP validation, timestamp precision/timezone, and representative Unicode collisions; and log/report redaction. Sequence and next-generated-ID tests run only in an isolated synthetic database.

Password verification tests may use only temporary credentials and synthetic Django-generated supported hashes. Test success and failure internally; do not persist credentials or export hashes/results that reveal them. Confirm the target session table remains empty. These tests do not establish production hash compatibility, actual source counts, or actual source collision rates.

## Rehearsal PASS/FAIL and Scope

**PASS** requires all named data-owner and security approvals and all fixture, isolation, no-egress, and artifact-retention gates to be evidenced; an unchanged approved fixture/mapping; zero unexplained count, key-set, UUID, or FK differences; zero unapproved rejected records; verified sequence behavior in the isolated synthetic database; and successful synthetic restart, failure-recovery, and redaction tests. Any exported report must contain only security-approved aggregates.

**FAIL / STOP** on any missing or unnamed approval; uncertain fixture provenance or failed sanitization; prohibited content in the fixture; production connectivity or possible outbound egress; unapproved artifact handling; changed fixture/mapping; unexplained reconciliation differences; unapproved rejected records; unsafe sequence behavior; partial batch, unexpected conflict, or failed restart/failure test; or sensitive content in logs/reports. Do not skip, silently repair, or continue past a stop condition.

Production systems and data, production credentials, source sessions, production migration/cutover, and Phase 5 are out of scope. This plan authorizes none of them.

## Rehearsal Sequence

1. **Authorize and freeze the source contract.** Do not begin fixture creation or rehearsal until named, recorded data-owner/security approvals and every fixture, isolation, no-egress, and artifact gate are evidenced. Only then may the approved source version/migration state/schema fingerprint and target PostgreSQL configuration be identified under that approval. Resolve only the approved framework-table scope and collision policy. Password preservation/reset and any cutover session policy remain undecided, require separate named, recorded approval, and authorize no source hash/session access.
2. **Prepare and validate a safe fixture.** Prefer generated synthetic rows. A source-derived fixture requires the approvals above and must be sanitized within its approved protected boundary before transfer. Exclude the source password column and `django_session` before fixture creation; validate their absence structurally without inspecting their values. The fixture must contain no prohibited secrets, credentials, password hashes, session data, or identifying content. Reject the entire fixture and stop immediately if any prohibited content is found; do not redact it in place and continue. Preserve only approved structural characteristics needed for range, nullability, length, relationships, and collation tests. Record sanitization limitations; synthetic values cannot establish production counts or collisions.
3. **Verify backup and restore.** Hash the approved protected backup manifest and restore only the sanitized fixture to a uniquely named ephemeral environment. Verify source password/session fields are absent by schema/table inspection without inspecting their values. Reject the fixture and stop immediately if prohibited content is found. Do not use existing databases or containers.
4. **Run read-only inventory on the approved isolated copy.** Count approved mapped and framework tables; inspect min/max IDs and the four positive-bigint fields; count null/blank values and field lengths; identify duplicate target keys; count status distributions, JSON validity, site-settings cardinality, soft-deleted rows, and FK orphans. Do not inspect, count, or query source sessions or password hashes. Keep detailed results inside the isolated environment; export only security-approved aggregates, with no identifiers or row-level results.
5. **Preflight transforms without writes.** Produce a deterministic field/ID mapping and reject values that exceed target ranges/lengths, violate checks, collide under PostgreSQL indexes or approved normalization rules, or reference unknown rows. Keep row-level diagnostics inside the isolated environment; export no identifiers, row-level digests, or sensitive comparison results. Stop on every unexplained discrepancy and every unapproved rejection.
6. **Future importer specification only.** This plan does not authorize importer implementation or execution. Any later isolated rehearsal import requires separate named, recorded data-owner/security approval and every fixture, isolation, no-egress, and artifact gate. If separately approved, use the specified fresh isolated test target and dependency order; preserve only approved IDs/UUIDs, keep target sessions empty, and do not dual-write. No production import is authorized.
7. **Reconcile.** Compare per-table row counts and PK/UUID sets; all FK references and relationship cardinalities; status/soft-delete/null/blank distributions; JSON and timestamps; counter recomputations; and approved attachment metadata/file checks inside the isolated environment. Do not export row-level digests, identifiers, or sensitive comparison results. Verify sequences and next-generated-ID behavior only in an isolated synthetic database. Ensure infrastructure stores were not created or changed.
8. **Validate auth without exposing secrets.** Test candidate verification only against synthetic Django-generated Argon2 and supported PBKDF2 hashes using temporary synthetic credentials that are not written to docs or logs. Test success/failure internally; output only security-approved aggregate pass/fail counts. Never access or inspect source password hashes. Actual production hash policy requires separate approval.
9. **Rehearse restore and failure recovery.** Restore the target backup to a second uniquely named isolated test database and repeat catalog/count assertions. Inject failures before, during, and after each batch commit; verify transaction atomicity and the specified restart behavior with no duplicates or inconsistent rows. Run sequence/next-generated-ID tests only in the isolated synthetic database. Discard only resources positively verified as created for that rehearsal and record deletion evidence for all artifacts under the approved retention policy.
10. **Review and stop.** Apply the PASS/FAIL criteria above. Require a signed, security-approved aggregate report and explicit rehearsal approval. A passing rehearsal authorizes neither production migration nor Phase 5 work.

## Acceptance and Stop Conditions

PASS only when: all table/column mappings and mandatory named data-owner/security approvals are recorded; fixture provenance, sanitization, isolation, enforced no-egress, and artifact retention/deletion controls are evidenced; counts, key sets, UUIDs, and FK relationships have zero unexplained differences; there are zero unapproved rejected records; all values fit approved target types/checks; collisions have an approved disposition; sequence behavior is verified only in an isolated synthetic database; synthetic password tests emit no secret output; sessions remain empty; batch atomicity, restart, failure recovery, restore, and redaction tests pass; and only security-approved aggregate results are exported.

FAIL / STOP before fixture creation or rehearsal if required named approvals are absent; stop and reject the fixture if provenance or sanitization is uncertain or any prohibited secret, password hash, session data, or identifying content is found; stop if production connectivity or outbound egress cannot be ruled out, artifact retention/deletion is unapproved, framework rows have unexplained dependencies, numeric/length/check constraints fail, Unicode equivalence is unresolved, backup verification fails, reconciliation has unexplained differences, any rejected record lacks approval, a batch is partial/mismatching, sequence/restart/failure tests fail, sensitive results are exported, or rollback could overwrite new mail/files. No production access, production migration, source-session handling, or Phase 5 is authorized by meeting rehearsal criteria.
