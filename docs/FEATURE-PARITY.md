# MailStack Feature-Parity Checklist

> **Authoritative database policy:** ReadBox uses exactly one PostgreSQL database for all application and database-backed mail-server management data. Prisma remains the application ORM. Any future Postfix/Dovecot database integration must use this same PostgreSQL database, with separate schemas and least-privilege roles where supported, after installed versions, configuration, schema, and lookup contract are verified. Do not add or connect MariaDB, MySQL, SQLite, or a second database. Maildir and message/attachment files remain on the filesystem. Any legacy multi-database descriptions below are historical/source context only and are superseded as target architecture.

## How to Use This Checklist

This checklist is based on inspected source in `reference/MailStack/`, not only its prose feature matrix. Every unchecked item is required before declaring parity. “Current behavior” wins over a feature label when they differ; unresolved differences are called out below. ReadBox has a replacement foundation, but feature parity remains incomplete.

## Accounts, Authentication, and Authorization

- [ ] Preserve the private login/logout flow; no public registration.
- [ ] Preserve the current administrator test (`is_staff` or `is_superuser`) and protect administrator-only operations.
- [ ] Preserve active/inactive user state, case-insensitive username uniqueness, admin-managed create/edit/delete, and restrictions against modifying/deleting admin users through this UI.
- [ ] Preserve last-active-admin/self-delete protections and mailbox/message retention on user deletion.
- [ ] Preserve Argon2 verification for existing Django password hashes or provide an approved, tested password reset transition. Do not silently hash/reset all passwords.
- [ ] Preserve 12-character minimum and Django's common/numeric/user-similarity password validators unless a reviewed policy change is approved.
- [ ] Preserve failed-login tracking by normalized username + IP, configured rolling window/limit/lockout, cleanup of old attempts, success cleanup, and audit events.
- [ ] Preserve session expiry, browser-close expiry, secure/HttpOnly/SameSite cookie policy, CSRF protection, safe `next` redirect validation, logout by POST, and trusted-proxy IP rules.
- [ ] Preserve user-to-mailbox memberships and independent `can_delete_messages` / `can_delete_mailboxes` grants; non-admin users must never access unassigned mailbox/message objects.
- [ ] Preserve admin audit records and redaction of password/secret/token/cookie/session/authorization/credential/private-key fields.

## Domains and Mailboxes

- [ ] Preserve domain create/edit/enable/disable/delete, default-domain choice and requirement that only active, DNS-verified domains are enabled/defaulted.
- [ ] Preserve generated DNS preview and full-record status checks for MX, expected A/AAAA, SPF, DKIM and DMARC. Keep activation verification separate: current `domain_check` verifies expected MX plus at least one A/AAAA answer for the configured mail hostname; it does not require SPF/DKIM/DMARC success, and a successful check does not automatically enable a disabled domain.
- [ ] Preserve reserved `postmaster` and `abuse` mailbox provisioning and safe initial-admin/system-mailbox bootstrap behavior.
- [ ] Preserve mailbox address/local-part validation, case-insensitive uniqueness, configured quota, canonical Maildir-relative path, and collision checks against active aliases/mail-server rows.
- [ ] Preserve ordinary-user mailbox self-service creation (the new mailbox is assigned to its creator); admins may assign new mailboxes to active non-admin users.
- [ ] Preserve mailbox creation as coordinated filesystem + application record + mail-server row + membership operation, with lock, compensation and failure audit.
- [ ] Preserve recipient activation/deactivation in the MariaDB mail schema so Postfix lookup behavior changes consistently with app state.
- [ ] Preserve user-visible mailbox search, status filtering, pagination, counts, shared membership and admin panel controls.
- [ ] Preserve bulk deletion, exact-address confirmation where currently required, and operation audit.
- [ ] Resolve deletion contract before implementation: `soft_delete_mailbox()` exists, and model has `deleted` state, but both current UI delete handlers call `purge_mailbox()`. The UI's confirmed delete permanently removes app records, mail-server row, Maildir and extracted attachment files. Do not substitute soft delete without product approval.

## Messages, MIME, and Attachments

- [ ] Preserve mailbox-scoped inbox access and message detail routes.
- [ ] Preserve search over sender address/subject; read/unread and attachment filters; 30-message pagination; received-time ordering; preview text behavior.
- [ ] Preserve auto-mark-read on detail open, explicit mark-unread, unread/total/last-received counters, and counter-rebuild command.
- [ ] Preserve message soft deletion (`deleted_at`, actor) without deleting the authoritative Maildir source; filter deleted records from normal queries.
- [ ] Preserve bounded live polling: authenticated and membership-filtered messages, cursor/bootstrap behavior, payload limits, no-store response, background request signature, summary and notification data.
- [ ] Preserve MIME header decoding, recipients/CC, date recovery, malformed-message recovery, plain-text fallback, parse statuses/warnings and source SHA-256.
- [ ] Preserve the HTML tag/attribute/protocol allowlist, CSS parsing budgets/properties/functions, remote image blocking, active-content removal, link handling, and the restrictive HTML-reader CSP/sandbox/referrer boundary.
- [ ] Preserve attachment extraction limits, filename normalization, MIME metadata, content hashes, random stored names, private file mode, path confinement, and inline metadata.
- [ ] Preserve object-scoped attachment authorization, internal Nginx acceleration where configured, download headers (`attachment`, `nosniff`, private/no-store), and 404 behavior without storage path disclosure.
- [ ] Preserve oversized message handling, idempotent `(mailbox, source_file_key)` deduplication, restart/retry safety, per-file failure continuation, exclusive worker lock, and heartbeat.
- [ ] Preserve operator commands for one-shot/watch/dry-run ingestion, missing-index rebuild, counter rebuild, Maildir verification, Postfix contract verification, and guarded body-only repair from hash-matching Maildir source.
- [ ] Preserve Maildir `new`/`cur` as read-only source from the indexer; do not move/delete received files during routine ingestion.

## Verified Mailbox Delete and Rebuild Nuances

Two implementation details need explicit acceptance tests rather than relying on labels:

1. The `rebuild_missing` option is passed to ingestion and recorded in heartbeat details, but the current scan already attempts all unindexed Maildir files regardless of this flag. `rebuild_mail_index` therefore uses the same scan with the flag set; verify intended parity against actual deployed behavior.
2. Soft mailbox deletion code is not called from the current web routes. Current user-visible mailbox deletion is permanent purge after permission and confirmation checks.

## Admin, Health, and Operations UI

- [ ] Preserve dashboard counts, recent messages/mailboxes, and admin-only storage/database/ingestion status visibility.
- [ ] Preserve admin-editable site settings and current public site-settings response, including origin-restricted CORS behavior.
- [ ] Preserve system-update page and admin-only release check, preflight, start-request and status behavior. Requests must be restricted to official GitHub release URLs and verified archive/checksum; execution stays out of the web process.
- [ ] Preserve live `/health/live/` and `/health/ready/` response behavior and status codes. Readiness checks database/migration state, storage writability and required configuration; it does not itself prove Postfix/Dovecot delivery.
- [ ] Preserve structured application logs, service heartbeat, audit event details, health scripts and application contract verification.
- [ ] Preserve installer plan mode, clean install, repair behavior, generated secrets/permissions, acceptance checks, and failure-safe operation.
- [ ] Preserve verified backup, restore, upgrade snapshot, rollback boundaries, checksum/archive validation and service-state restoration. Adapt them for PostgreSQL before cutover.

## Public Website and Contact Service

- [ ] Keep current static public pages/assets and contact/privacy URLs unless separately approved.
- [ ] Preserve contact `GET /csrf/`, `POST /`, `GET /health/` through Nginx `/api/contact/` routing.
- [ ] Preserve one-use CSRF token bound to Secure/HttpOnly/SameSite=Strict cookie and configured expiry.
- [ ] Preserve JSON content type and 32 KiB request limit; field validation, consent, honeypot, 2.5-second minimum and 24-hour maximum form age.
- [ ] Preserve HMAC-hashed IP/email identifiers and limits (5/IP/15 min, 20/IP/day, 3/email/hour), `Retry-After`, SQLite transaction behavior and submission delivery states.
- [ ] Preserve fixed local sendmail path/arguments/timeout, fixed recipient, reply-to validation, header-injection protection, failure persistence and 503 behavior. User input must never select the executable/recipient.
- [ ] Preserve separate process identity, Unix socket, restricted address families, state directory permissions and contact health endpoint.

## UI and PWA Requirements

- [ ] Build with Next.js App Router, TypeScript, Tailwind CSS and shadcn/ui; retain compact, clean, professional webmail/admin workflows.
- [ ] Use Segoe UI as the only named typeface. Do not redistribute a bundled Segoe font without license approval; verify system fallback on supported Ubuntu/browser environments.
- [ ] Provide shared centralized design tokens and consistent light and dark themes across user/admin panels; keep components reusable and responsive.
- [ ] Add app manifest, installability metadata/icons and service-worker lifecycle. Service worker may cache versioned public/static resources only; authenticated pages, messages, attachments and API responses must remain network-only/no-store.
- [ ] Test at 320, 768 and 1280 CSS-pixel viewport widths, keyboard navigation, focus visibility, contrast in both themes, install prompt eligibility and cache exclusions.

[Its UI test](../tests/ui/app-shell.test.tsx) covers focus entry, Escape/close restoration, Tab/Shift+Tab boundary cycling, and simulated breakpoint changes. [Theme token tests](../tests/ui/theme-contrast.test.tsx) verify small muted text meets 4.5:1 contrast on the tested light/dark surfaces. [The reduced-motion test](../tests/ui/reduced-motion.test.tsx) verifies the CSS contract under `prefers-reduced-motion: reduce`; it does not verify browser rendering or live preference changes. [The theme-toggle test](../tests/ui/theme-toggle.test.tsx) verifies keyboard activation in both directions.

**Latest browser QA — 2026-11-15 (Phase 7 Verified):** Headless Chromium (`playwright-cli`) verified `/sign-in`, `/reset-password`, `/users`, `/users/mailboxes`, `/vcon`, `/vcon/domains`, `/vcon/domains/new`, `/vcon/mailboxes`, `/vcon/mailboxes/new`, `/vcon/users`, `/vcon/users/new`, `/vcon/operations`, `/vcon/audit`, `/vcon/settings`, and `/vcon/system-update` across `320px`, `768px`, and `1280px` viewports in both **Light** and **Dark** themes (`scrollWidth === clientWidth`, `overflow: false`, `0` console errors). These are explicit target requirements, not existing webmail features. The current app has a Segoe UI/system fallback, an authenticated-app manifest, production-only service-worker registration, and a worker that limits caching to offline fallback and immutable same-origin static assets. Latest reported automated totals were 87/87 component-independent tests and 21/21 UI tests; focused reduced-motion, manifest, and service-worker tests passed 7/7. Component/static tests cover manifest icons, registration conditions, worker lifecycle, cache exclusions, muted-text contrast tokens, keyboard theme-toggle activation, and the reduced-motion CSS contract. Real-browser viewport acceptance is incomplete, light-theme appearance is unverified, and app-level reduced-motion rendering, production service-worker registration, installability, and supported-platform font fallback remain pending. The static public site has its own manifest; do not confuse that manifest with the authenticated app.

## Test Parity Map

Use original tests as behavioral fixtures/oracles and port the cases into Node tests. The original suites cover:

- `tests/unit/`: validators, models, domain rules, mail-server adapter, parser/storage, provisioning and configurability.
- `tests/integration/`: auth, health/Postfix commands, mail-server sync, message repair, access/live/delete.
- `tests/functional/`: compact mailbox reader, responsive/routes, site settings, update flow and shared UI foundation.
- `tests/reliability/`: restart idempotency, malformed + valid continuation, transient DB failure, late Maildir delivery, provisioning failure and counter rebuild.
- `tests/security/`: CSRF, allowed hosts, security headers, sanitizer, XSS, path confinement, protected attachment behavior, audit redaction, cookie flags and deployment contracts.
- `public-site/contact_service/test_contact_app.py`: CSRF, cookie, validation, abuse checks, persisted status, one-time token and DB connection closure.

Passing new tests must be demonstrated; historical test claims in repository docs are not a substitute for running the Phase 2 suite.
