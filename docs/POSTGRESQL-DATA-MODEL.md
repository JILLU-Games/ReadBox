# PostgreSQL Data Model and Migration Mapping

> **Authoritative database policy:** ReadBox uses exactly one PostgreSQL database for all application and database-backed mail-server management data. Prisma remains the application ORM. Any future Postfix/Dovecot database integration must use this same PostgreSQL database, with separate schemas and least-privilege roles where supported, after installed versions, configuration, schema, and lookup contract are verified. Do not add or connect MariaDB, MySQL, SQLite, or a second database. Maildir and message/attachment files remain on the filesystem. Any legacy multi-database descriptions below are historical/source context only and are superseded as target architecture.

## Scope and Safety

This model is based on the inspected Django models/migrations at `reference/MailStack/`. It is the new application's PostgreSQL schema only. It does **not** replace or copy the separate MariaDB schema used by Postfix/Dovecot, and it does not absorb the contact service's SQLite state. The generated `prisma/migrations/20261017000000_initial_application_schema/migration.sql` was applied only to a newly created, disposable PostgreSQL 16.14 rehearsal container; it remains unapplied in persistent or production environments. No production database was queried or changed.

The migration and cutover content below is future planning, not authorization. Production access, production migration, cutover, and Phase 5 remain unapproved. During rehearsal, never inspect, count, copy, or import source sessions and never access or inspect source password hashes; password verification is synthetic-only.

Phase 4 Prisma schema and initial SQL are complete; the isolated PostgreSQL 16.14 Phase 4.1 schema-only rehearsal passed; and Phase 4.2 risk/rehearsal planning is complete. No source-data migration or source-data rehearsal has been performed, and no importer implementation or data-import command has been established. PostgreSQL `lower()` is not full Unicode casefold (`Straße` and `STRASSE` remain distinct under the tested behavior). Production collation, ID ranges, password compatibility, sessions, backup/restore, and rollback remain untested.

Any future fixture or rehearsal requires named data-owner and security approval, approved provenance and sanitization, enforced production disconnection and outbound network denial, and an approved artifact retention/deletion policy with verified deletion evidence. Reject the entire fixture and stop immediately if validation finds any prohibited secret, password hash, session data, or identifying content.

Approvals must be named and recorded before any source/production inventory, backup, restore, or data access. They must include fixture provenance/sanitization evidence, verified production disconnection, tested outbound denial including external/AI egress, approved artifact access/retention/deletion, and verified deletion evidence for fixtures, logs, checkpoints/manifests, temporary files, reports, backups, and disposable targets. No such access or fixture activity is authorized now.

- PostgreSQL image/version: local `postgres:16-alpine`, server `16.14` (PostgreSQL 16.14 on Alpine Linux); database encoding `UTF8`, `datcollate` and `datctype` both `en_US.utf8`.
- Exact SQL tested: `prisma/migrations/20261017000000_initial_application_schema/migration.sql`; SHA-256 `7839ada483c61d6fabc7c80ee57dd4ae4d739a21e46eab38e7c116bcb047e3eb`.
- Isolation: newly created container `mailstack-phase41-e3cda607f6214efe95d1cd48934ae11c`, labeled for Phase 4.1; Docker `none` network, no port bindings, no external volume, PostgreSQL data on 512 MiB tmpfs, randomly generated temporary password (not recorded). The container and temporary probe SQL were removed after evidence collection.
- `CREATE DATABASE mailstack_phase41_rehearsal` succeeded. Applying the exact SQL with `psql -X -U mailstack_rehearsal -d mailstack_phase41_rehearsal -v ON_ERROR_STOP=1 -f /tmp/mailstack-initial-application-schema.sql` exited `0`; PostgreSQL emitted only the expected notice that `public` already exists.
- Catalog verification: 12 expected application tables and 125 columns; this matches the 12 Prisma models and 125 scalar fields. All catalogued column types, lengths and nullability were compared with `schema.prisma`. There were 12 primary keys, 11 foreign keys, 7 check constraints, and all 16 expected non-primary unique indexes. The foreign keys reported 6 `CASCADE`, 4 `SET NULL`, and 1 `RESTRICT`, including `app_sessions.user_id -> users.id ON DELETE CASCADE`.
- All source query and FK-supporting indexes were present, including lower-expression unique indexes for username, domain name, mailbox local part per domain and mailbox email. The catalog contained zero Postfix/Dovecot MariaDB tables/views or contact SQLite tables.
- Synthetic-only inserts confirmed ASCII case-insensitive uniqueness, `Ä`/`ä` lower-case uniqueness under `en_US.utf8`, all four functional unique-index behaviors, and deletion of a test user cascading its `AppSession` row. `Straße` and `STRASSE` remained distinct: PostgreSQL `lower()` is not full Unicode casefold. Do not treat this test as proof that `lower()` matches production MariaDB collation for all Unicode values.
- This was a schema-only rehearsal. No source rows, IDs, password hashes, message data, attachment bytes, or counters were imported or tested for preservation. No production database, MariaDB, mail server, Postfix, Dovecot, or Maildir was accessed.

The initial locale metadata probe used `SHOW lc_collate` and exited `1` because it is not a PostgreSQL configuration parameter; the corrected `pg_database.datcollate/datctype` query exited `0`. The first constraint report also exited `1` because `contype` needed an explicit text cast; the corrected catalog query exited `0`. Neither was a migration failure, and no migration SQL change was needed.

The Node schema uses normalized table/column names. A future importer specification must use the source-table mapping below and define ID/UUID/FK handling. Detailed reconciliation belongs inside the isolated environment; only security-approved aggregates may be exported, with no row-level digests, identifiers, or sensitive comparisons. This description is not authorization to implement or run an importer. Django `BigAutoField` maps to PostgreSQL `BIGINT`; Django `PositiveBigIntegerField` maps to PostgreSQL `BIGINT` plus a nonnegative check, but MySQL unsigned values may exceed PostgreSQL's signed maximum. Preflight those values before an approved import. Timestamps use PostgreSQL `TIMESTAMPTZ(6)`; Django JSON fields use JSONB; file fields become persisted storage-relative strings, not file bytes.

## Constraint and Index Decisions

- Any source/production collation, ID-range, numeric-bound, or unsupported-value inspection requires separate named, recorded data-owner and security approval and all applicable safety gates. No such inventory or data access is authorized now; rehearsal mechanics use only approved sanitized data and synthetic tests as specified in the rehearsal plan.

- `BigInt` primary keys preserve Django `BigAutoField` identity. The future importer specification must preserve explicit IDs and define sequence reset behavior, including empty tables. Do not execute sequence resets or next-generated-ID tests on sanitized-source fixtures; test only in an isolated synthetic database. This specification is not permission to implement or run an importer.
- PostgreSQL is case-sensitive by default, unlike the source `utf8mb4_unicode_ci` deployment and `Lower(...)` constraints. The SQL adds unique functional indexes for lower(username), lower(domain name), lower(mailbox email), and `(domain_id, lower(local_part))`. The rehearsal confirmed ASCII and accented-Latin case pairs under `en_US.utf8`, but also confirmed that `lower()` does not implement full Unicode casefold (`Straße` and `STRASSE` remain distinct). Preflight all case/Unicode collisions against the actual source collation; never merge automatically.
- Custom SQL adds finite status checks for domain status, domain verification state, mailbox status and message parse state; it also preserves nonnegative Django positive-big-integer fields.
- PostgreSQL `BIGINT` tops out at 9,223,372,036,854,775,807, while MySQL unsigned bigint fields can reach 18,446,744,073,709,551,615. Preflight message/attachment sizes and mailbox counters; stop for an approved wider/numeric/string representation if any source value exceeds the signed range.
- Preserve all verified indexes supporting source queries and the unique Maildir source key. Keep JSONB and UTC timestamps. Do not add a unique default-domain constraint or business rules absent from source.
- PostgreSQL does not automatically index foreign-key columns. The initial SQL explicitly indexes mailbox domain/deletion actor, membership assigner, message deletion actor, attachment message, and audit actor references, plus standalone mailbox creation-time and message read-state fields from the source model.
- `SiteSettings` remains operationally a `pk=1` row but the source has no singleton DB constraint. Migration should retain row identity and detect multiple rows for owner review.
- Some `updated_at` fields have no database default because Prisma `@updatedAt` supplies values on application writes. Importers must explicitly populate timestamps for historical rows.
